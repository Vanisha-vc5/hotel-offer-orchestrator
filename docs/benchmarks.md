# Request-coalescing benchmark

> **100 concurrent requests → 6 workflow runs, 12 supplier calls (vs 100 runs and 200 calls without coalescing)**

Generated by `npm run benchmark` (`scripts/benchmark.ts`). Each level fires N simultaneous
`GET /api/hotels?city=delhi` requests and waits for all of them. "Coalescing off" uses the
`X-Coalescing: off` operator override (`FEATURE_BENCHMARK=true`), which gives every request its own
workflow ID. Supplier calls come from the mock suppliers' Redis counters
(`GET /admin/metrics/suppliers`); health and monitor probes are not counted.

## Interpretation

With coalescing off, every request starts its own workflow, so workflow runs and supplier calls grow linearly with N (200 runs and 400 supplier calls at N=200). With coalescing on, concurrent requests attach to the run already in flight for `hotel-offers-delhi` (`workflowIdConflictPolicy: USE_EXISTING`), and runs grow far more slowly (1 at N=1, 1 at N=10, 3 at N=50, 6 at N=100, 12 at N=200). They don't collapse to exactly one because a burst of N requests reaches Temporal spread over time (the API issues N start calls), while a run lasts only ~150 ms. A request arriving after a run has closed correctly starts a fresh one (`ALLOW_DUPLICATE`): fresh data, never a stale result. At N=200 that means 16.7× less supplier traffic and a p95 of 2354 ms instead of 11276 ms (4.8× faster), because Temporal and the suppliers do a fraction of the work. Absolute latencies come from one laptop running every service in Docker; the ratios are what matters.
